# AGENTS.md — контракт команды и агентов

> Этот файл Codex читает автоматически в начале каждой сессии. Всё, что агент обязан знать, лежит здесь, а не в чате.
> Владелец файла — **роль A**. Остальные не редактируют его; запросы на изменение пишут в `docs/requests/<буква>.md`.

---

## 1. Миссия

Хакатон HackAlem, трек «Добывающая промышленность». 5 часов. Строим **PermitGuard** — предсменного инспектора наряда-допуска.

На вход приходит комплект документов (PDF/сканы наряда, карточки работников, журнал газоанализа, перечень изоляций). Система извлекает поля, вызывает mock-реестры, применяет детерминированные правила и выдаёт вердикт с доказательными ссылками. Система **никогда не разрешает работы** — она формирует рекомендацию уполномоченному лицу.

Победа — не объём кода, а: рабочее демо на ловушечном комплекте + прохождение автотеста + понятный жюри питч.

## 2. Жёсткие правила (нарушение = проваленная задача)

1. **Prooflinks обязательны.** Любой вывод без `source_id` + `location` + `quote` считается несуществующим. Модель не имеет права утверждать то, на что не может показать пальцем.
2. **Честное незнание.** Разрешённые статусы находки: `confirmed`, `contested`, `unknown`, `insufficient_evidence`. Выдумка штрафуется сильнее осторожного пропуска. Запрещено заполнять поле догадкой, чтобы «схема была валидной».
3. **Fail-closed.** Неполные или противоречивые данные → статус `block_and_escalate` с причиной, а не `approve`.
4. **HITL.** Итоговый вердикт — рекомендация человеку. В UI и в JSON всегда присутствует `requires_human_review` и `required_human_decision`.
5. **Минимум один вызов mock-API за прогон** (`employee_clearance`, `gas_test_status`, `asset_isolation`, `site_restrictions`).
6. **Минимум один детерминированный валидатор.** Правила допуска исполняются кодом (Python + Pydantic), а не рассуждением модели. Любая арифметика (сроки, пересечения интервалов, время действия газоанализа) — кодом.
7. **Никакой ML-магии.** Ничего не обучаем, датасеты не размечаем, к реальному «железу» не подключаемся. Все данные синтетические.

## 3. Контракт результата (заморожен на T+45, менять может только роль A)

Единый формат, требуемый организатором:

```json
{
  "task_id": "permitguard",
  "run_id": "demo-001",
  "status": "completed",
  "verdict": "block_and_escalate",
  "findings": [
    {
      "finding_id": "F-014",
      "rule_id": "R-GAS-02",
      "severity": "P1",
      "classification": "confirmed",
      "claim": "Газоанализ просрочен на момент начала работ.",
      "confidence": 0.94,
      "prooflinks": [
        { "source_id": "permit_0042.pdf", "location": "page:2", "quote": "..." },
        { "source_id": "gas_log_2026-09-20.csv", "location": "row:118", "quote": "..." }
      ],
      "validation": {
        "rules_passed": ["R-SIG-01"],
        "rules_failed": ["R-GAS-02"],
        "unknowns": ["Статус изоляции не подтверждён реестром"]
      },
      "requires_human_review": true,
      "required_human_decision": "Руководитель работ обязан подтвердить повторный газоанализ"
    }
  ],
  "unknowns": [],
  "audit_log": []
}
```

Значения `verdict`: `approve` | `approve_with_conditions` | `block_and_escalate`.
Источник истины по схеме — `core/schemas.py` (Pydantic v2). JSON выше и схема обязаны совпадать; при расхождении прав `core/schemas.py`.

## 6. Git

- Ветка одна: `main`. Перед каждым пушем: `git pull --rebase origin main`.
- `git add` — только свои каталоги. `git add -A` из корня запрещён.
- Сообщение коммита: `[A|B|C] область: что сделано` (например `[B] data: 20 комплектов с зашитыми нарушениями`).
- Пуш каждые 10–15 минут, маленькими коммитами.
- **Запрещено:** `git push --force`, `git reset --hard` на общей ветке, переписывание истории, удаление чужих файлов, коммит `.env`, коммит `.venv` и бинарников > 5 МБ.
- Конфликт rebase → `git rebase --abort`, вынести правку в ветку `feat/<буква>-<тема>`, сообщить роли A.

## 7. Определение готовности (Definition of Done)

Задача не закрыта, пока не выполнено всё:

```bash
make smoke          # сквозной прогон на одном комплекте, без исключений
make eval           # печатает метрики
make test           # pytest зелёный
```

Цели уже описаны в `Makefile`; трогать его может только роль A. Быстрый срез состояния всей команды: `./checkpoint.sh --quick`.

Метрики приёмки: recall по 20 зашитым нарушениям ≥ 0.8; ложных `approve` на критических кейсах — **ноль**; каждый `finding` имеет минимум один валидный prooflink (проверяется автоматически: `source_id` существует, `location` указывает на реальную строку/страницу).

«Я реализовал» без зелёного вывода этих трёх команд не считается результатом. Если не сходится с третьей попытки — останови работу, напиши блокеры в `docs/requests/<буква>.md` и сообщи человеку одной строкой.

## 8. Как работать (порядок для агента)

1. Прочитай этот файл и `docs/plan-<буква>.md`, если он есть.
2. **Сначала план, потом код.** Первым сообщением сессии — план в `docs/plan-<буква>.md`: шаги, файлы, критерий готовности каждого шага. Остановись и дождись подтверждения человека.
3. Работай тонкими вертикальными срезами: сначала сквозной путь на одном комплекте документов, потом качество и охват. Никогда «сначала все модели, потом все правила».
4. После каждого среза: `$verification-loop`, затем коммит и пуш.
5. Полезные скиллы ECC: `$contract-first`, `$api-design`, `$python-patterns`, `$regex-vs-llm-structured-text`, `$eval-harness`, `$verification-loop`, `$orch-fix-defect`, `$frontend-patterns`, `$frontend-slides`, `$safety-guard`.
6. Внешние скиллы вендорены в `.agents/skills/`. Перед работой над UI прочитай `.agents/skills/ui-ux-pro-max/SKILL.md`; перед разбором PDF — `.agents/skills/anydoc/SKILL.md`.
