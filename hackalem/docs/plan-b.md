# План роли B: данные и извлечение

## Границы работы

- Рабочие каталоги роли B: `data/` и `extract/`. Этот файл плана — единственное изменение до одобрения.
- Контракты читать из `core/schemas.py`, потребление эталона — из `eval/`, идентификаторы правил — из `rules/matrix.yaml`; не дублировать и не переопределять их в слое B.
- Все данные синтетические. Реальные персональные данные, внешние реестры и обучение моделей не используются.
- Любое извлечённое значение сопровождается `source_id`, точным `location` и дословной `quote`. Отсутствующее, противоречивое или неподтверждённое значение возвращается как `None` со статусом `insufficient_evidence`.
- Извлечение не принимает решение о допуске и не вычисляет вердикт: арифметика и правила остаются в детерминированном слое правил.

## 1. Зафиксировать контракты первого среза

**Файлы:** чтение `core/schemas.py`, `eval/run.py`, `eval/metrics.py`, `rules/matrix.yaml`; при необходимости запрос в `docs/requests/b.md`.

1. Выписать обязательные поля входного комплекта, формат результата извлечения, допустимые статусы и структуру prooflink.
2. Сверить канонические `rule_id` для шести контролируемых нарушений. Не вводить временные идентификаторы, если контракт другой роли ещё не готов.
3. Зафиксировать формат `data/ground_truth.json`, который фактически читает eval роли A, до массовой генерации данных.
4. Определить единые правила адресации: PDF — `page:<номер с 1>`, CSV — `row:<номер физической строки с 1>`, JSON — стабильный JSON Pointer либо формат, уже принятый в `core/schemas.py`.

**Критерий готовности:** один сгенерированный комплект и одна запись ground truth проходят загрузку Pydantic-схемой и читаются eval без преобразований и локальных обходов контракта.

## 2. Каноническая спецификация синтетического кейса

**Файлы:** `data/generator.py`, внутренние структуры только внутри `data/`.

1. Описать кейс одной детерминированной спецификацией: `permit_id`, seed, зона, актив, вид и интервал работ, смена, работники и срок допуска, подписи, газоанализ и срок его действия, LOTO, параллельные работы.
2. Из одной спецификации строить четыре согласованных документа:
   - `permit_XXXX.pdf` — текстовый PDF наряда-допуска;
   - `employee_card.json` — карточка работника;
   - `gas_log.csv` — выписка журнала газоанализа;
   - `isolations.csv` — перечень изоляций.
3. Использовать фиксированный seed, стабильную сортировку, фиксированную кодировку UTF-8 и предсказуемые даты относительно заданного `reference_time`, а не текущего времени машины.
4. Разделить корректную базовую спецификацию и явные функции-инъекторы нарушений. Инъектор меняет только минимально необходимое поле и регистрирует ожидаемое нарушение и его источник.
5. Не имитировать сканы в первом срезе: PDF должен содержать извлекаемый текст. Сценарии изображения/vision добавить только после зелёного текстового пути.

**Критерий готовности:** повторный запуск с тем же seed создаёт семантически одинаковые документы; все четыре файла согласованы по идентификаторам, времени, зоне, активу и работнику.

## 3. Первые 10 комплектов и эталон

**Файлы:** `data/generator.py`, `data/fixtures/permit_0001/` … `permit_0010/`, `data/ground_truth.json`.

1. Создать 10 комплектов: корректные случаи и минимум по одному примеру каждого из шести нарушений.
2. Для каждого комплекта записать в ground truth полный список ожидаемых нарушений. Для каждой записи хранить канонический `rule_id`, тип нарушения и prooflink с существующими `source_id`, `location`, `quote`.
3. Ground truth формировать из той же спецификации кейса, но проверять обратным чтением уже созданных файлов: цитата обязана буквально находиться в указанном документе, страница или строка обязана существовать.
4. Корректные кейсы должны иметь пустой список нарушений. Пропущенное обязательное поле оформлять отдельно как `insufficient_evidence`, не маскировать под другое нарушение.
5. Перед расширением до 60 прогнать загрузку eval роли A и устранить только несовместимости слоя B; изменения чужих контрактов запрашивать через `docs/requests/b.md`.

**Критерий готовности:** eval читает все 10 кейсов; валидатор ground truth подтверждает существование каждого файла, адреса и цитаты; корректные кейсы не содержат случайно зашитых нарушений.

## 4. Масштабирование до 60 комплектов

**Файлы:** `data/generator.py`, `data/fixtures/permit_0001/` … `permit_0060/`, `data/ground_truth.json`.

1. Сформировать 40 корректных и 20 ловушечных комплектов.
2. В 20 ловушечных кейсах зафиксировать ровно 20 основных контролируемых нарушений, чтобы знаменатель recall был однозначным:
   - 4 просроченных газоанализа;
   - 4 отсутствующие обязательные подписи;
   - 3 неверные зоны работ;
   - 3 конфликта несовместимых одновременных работ;
   - 3 просроченных допуска работника;
   - 3 неподтверждённые LOTO-изоляции.
3. Варьировать безопасные параметры: работников, активы, зоны, виды работ, даты и порядок строк. Не менять смысл контрольного нарушения декоративными вариациями.
4. Проверить отсутствие скрытых дополнительных нарушений в 40 корректных кейсах и отсутствие второго незаявленного нарушения в каждом ловушечном кейсе.
5. Сделать генерацию идемпотентной: известные файлы конкретного кейса перезаписываются детерминированно, посторонние пути не удаляются.

**Критерий готовности:** ровно 60 валидных каталогов, 40 чистых кейсов, 20 ловушечных кейсов и 20 эталонных нарушений; распределение и ссылки подтверждены автоматическими тестами.

## 5. Детерминированное извлечение

**Файлы:** `extract/extractor.py`, при необходимости небольшие шаблоны в `extract/prompts/` только для fallback.

1. Реализовать единый вход: путь к каталогу комплекта; разрешать только ожидаемые форматы и выдавать понятную ошибку для отсутствующего или дублирующегося документа.
2. Извлекать PDF-текст через PyMuPDF постранично, CSV через стандартный `csv` с сохранением физического номера строки, JSON через стандартный парсер.
3. Разбирать маркированные поля PDF якорными regex-шаблонами; даты, время и идентификаторы нормализовать детерминированно. Не делать выводов о нарушениях на этапе извлечения.
4. Для каждого значения строить prooflink в момент чтения источника. После извлечения валидировать, что `quote` действительно присутствует по указанному адресу.
5. При отсутствии поля, неоднозначном совпадении, конфликте документов или ошибке формата возвращать честный статус (`insufficient_evidence`, `contested` или `unknown` по контракту), не выбирать значение догадкой.
6. Результат валидировать строгой Pydantic-схемой из `core/schemas.py`; локальную несовместимую копию схемы не создавать.

**Критерий готовности:** все поля текстовых 10 кейсов извлекаются повторяемо без сети; каждое непустое значение имеет валидный prooflink; пропуски не превращаются в вымышленные значения.

## 6. Опциональный OpenAI fallback

**Файлы:** `extract/extractor.py`, `extract/prompts/`; `extract/vision.py` — только для отдельного последующего сценария скана.

1. Вызывать fallback только для полей, которые детерминированный путь не смог извлечь однозначно. Успешные детерминированные значения модели не передавать на переоценку.
2. Включать fallback явным параметром и только при наличии `OPENAI_API_KEY` в окружении. Базовый smoke/test должен работать без ключа и без сети.
3. Использовать OpenAI structured outputs со строгой схемой. В контекст передавать минимальный фрагмент документа вместе с известными `source_id` и `location`.
4. Принимать ответ модели только после локальной проверки схемы и буквального наличия цитаты в источнике. Модель не может создавать имя файла, страницу, строку или цитату, которых нет.
5. Таймаут, отказ API, невалидный JSON, отсутствующая цитата или низкая доказательность приводят к `insufficient_evidence`; детерминированный результат сохраняется.
6. Vision не включать в обязательный путь первой версии. Для будущих сканов применять те же structured-output и prooflink-проверки, сохраняя номер страницы.

**Критерий готовности:** отключённый fallback не меняет детерминированный результат; замоканный успешный fallback заполняет только ранее неизвестное поле; любой невалидный ответ безопасно деградирует в `insufficient_evidence`.

## 7. Тесты

**Файлы:** тесты размещать внутри принадлежащих роли B каталогов, например `data/tests/test_generator.py` и `extract/tests/test_extractor.py`, если текущая конфигурация pytest их обнаруживает.

1. Генератор: одинаковый seed даёт одинаковые значения и ground truth; другой seed меняет только разрешённые вариации.
2. Структура: каждый комплект содержит ровно четыре ожидаемых документа с корректными именами и форматами.
3. Согласованность: идентификаторы, работник, зона, актив и временные поля совпадают между документами там, где должны совпадать.
4. Инъекторы: отдельный тест на каждый из шести типов; изменяется только целевое условие, а ground truth получает правильный канонический `rule_id`.
5. Prooflinks: каждый `source_id` существует, каждая страница/строка разрешается, каждая `quote` буквально найдена; отрицательные тесты отклоняют выдуманную цитату и адрес вне диапазона.
6. Извлечение: позитивные, отсутствующие, неоднозначные и противоречивые поля; проверка `None` и `insufficient_evidence` без догадок.
7. Fallback: тест без ключа, тест отключённого режима, замоканный успешный structured output, таймаут, ошибочная схема и выдуманная цитата. Реальные API-вызовы в unit-тестах запрещены.
8. Интеграция: как минимум один чистый и по одному кейсу каждого нарушения проходят путь «файлы → извлечение → схема → eval».

**Критерий готовности:** тесты слоя B зелёные и входят в общий `make test`; повторный прогон не зависит от сети, текущего времени или порядка файлов в ОС.

## 8. Финальная приёмка роли B

1. `make smoke` проходит на одном ловушечном комплекте без исключений.
2. `make eval` видит 60 комплектов и 20 эталонных нарушений; общий recall не ниже 0.8.
3. `make test` зелёный.
4. На критических кейсах нет ложного `approve`; неполные и противоречивые данные остаются fail-closed в сквозном результате.
5. Каждый finding, построенный из данных роли B, имеет хотя бы один prooflink, который указывает на существующий файл и реальную страницу/строку с совпадающей цитатой.
6. Ни один тест или обязательный demo-path не требует `OPENAI_API_KEY`; включение fallback не ухудшает проверяемость источников.

После одобрения выполнять план тонкими срезами в порядке разделов: контракт → 10 комплектов → детерминированное извлечение → 60 комплектов → опциональный fallback → полная приёмка.
