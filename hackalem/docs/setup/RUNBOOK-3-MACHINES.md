# HackAlem · Трек «Добывающая промышленность» — боевой регламент команды

**Состав:** 3 человека, 3 машины, 3 аккаунта Codex, 3 аккаунта GitHub, один общий репозиторий GitHub.
**Инструмент:** ECC (Everything Claude Code) как плагин Codex + набор внешних скиллов.
**Задача по умолчанию:** № 2 «PermitGuard — предсменный инспектор наряда-допуска» (паттерн 1: извлечение → детерминированная валидация → fail-closed вердикт с prooflinks и HITL). Замена на другую задачу — Приложение Б.

---

## 0. Главный принцип

Вы не пишете код. Вы владеете тремя рычагами, и только ими:

1. **Контракт до кода.** Всё, что агент должен знать о задаче, лежит в `AGENTS.md` репозитория, а не в чате. Codex читает его на старте каждой сессии — значит любая новая сессия у любого из троих стартует с одинаковым знанием.
2. **Машинная приёмка.** «Готово» — это зелёный `make smoke` и напечатанные метрики `eval/run.py`, а не фраза агента «I've implemented the feature».
3. **Таймбокс.** Агент буксует 10 минут — вы не спорите с ним, а перезапускаете сессию с чистым контекстом или переключаете на `$orch-fix-defect`.

Всё остальное (планирование, код, тесты, коммиты, рефакторинг, слайды) делает ECC.

# ЧАСТЬ I. Подготовка машины (делает каждый, за день до хакатона)

Время: 40–60 минут на машину. **Не делайте это на хакатоне** — Wi-Fi на 500 команд не выдержит `npm install`.

### Шаг 1. Проверить предусловия

```bash
node -v          # нужно >= 20 (минимум 18)
python3 -V       # нужно >= 3.11
git --version
codex --version
```

Чего нет — доставить: Node с nodejs.org или через nvm, Python 3.11+, Git.

### Шаг 2. Войти в свой аккаунт Codex

```bash
codex login          # у каждого СВОЙ аккаунт, ничего не расшаривается
codex --version
```

Проверка: `codex "скажи одно слово: ок"` должен ответить.

### Шаг 3. Установить ECC как нативный плагин Codex

```bash
codex plugin marketplace add affaan-m/ECC
codex plugin add ecc@ecc
codex plugin list --json
```

Обе команды идемпотентны — повторный запуск безопасен. После установки **перезапустите Codex**.

Проверка внутри Codex:

```
/plugins            # ECC должен быть в списке и enabled
$configure-ecc      # guided-настройка ECC (пройти один раз)
```

**Офлайн-резерв (если на площадке не будет интернета до GitHub):** у вас есть `ECC-main.zip`. Распакуйте его один раз в `~/tools/ECC` и поставьте из локального пути:

```bash
unzip ECC-main.zip -d ~/tools && mv ~/tools/ECC-main ~/tools/ECC
codex plugin marketplace add /home/$USER/tools/ECC
codex plugin add ecc@ecc
cd ~/tools/ECC && npm install --ignore-scripts && node scripts/codex/check-plugin-cache.js
```

Последняя команда проверяет, что установленный манифест действительно видит свои скиллы и конфиги.

### Шаг 4. Чего НЕ делать

- ❌ Не запускать `bash scripts/sync-ecc-to-codex.sh` вместе с нативным плагином — это два разных способа установки, вместе они дублируют скиллы и хуки.
- ❌ Не включать хуки ECC в Codex на хакатоне. Они требуют явного trust в `/hooks`, а при ошибке блокируют сессию. Скиллы работают и без них.
- ❌ Не ставить 20 скиллов «на всякий случай». Каждый скилл — это контекст. Правило: **максимум 3 внешних скилла на человека**.

### Шаг 5. Проверить, что скиллы вызываются

Внутри Codex в любой папке:

```
$tdd-workflow
```

Если агент подхватил инструкцию (а не сказал «не знаю такой команды») — ECC работает. Скиллы ECC вызываются через `$имя-скилла`. Полезные имена, которые понадобятся: `$plan-canvas`, `$contract-first`, `$api-design`, `$python-patterns`, `$eval-harness`, `$verification-loop`, `$orch-add-feature`, `$orch-fix-defect`, `$regex-vs-llm-structured-text`, `$frontend-slides`, `$ui-demo`, `$strategic-compact`, `$safety-guard`, `$git-workflow`.

### Шаг 6. Внешние скиллы (из `n_skills.txt`)

Ставим **только то, что реально нужно на 5 часов**. Берём три:

| Скилл | Кому | Зачем |
|---|---|---|
| `nextlevelbuilder/ui-ux-pro-max-skill` | Роль C | Витрина демо не выглядит как студенческий Streamlit |
| `cathrynlavery/diagram-design` | Роль C | Схема архитектуры на слайд за 3 минуты |
| `firecrawl/anydoc` (или `docling-project/docling-mcp`) | Роль B | Разбор PDF/сканов нарядов в структуру |

Опционально для питча: `N1arko/redaktura-skills` (редактура русского текста).

Надёжный способ подключения — **вендорить в репозиторий**, чтобы скилл был у всех троих и не зависел от настроек машины:

```bash
cd <репозиторий>
mkdir -p .agents/skills
git clone --depth 1 https://github.com/nextlevelbuilder/ui-ux-pro-max-skill /tmp/s1
cp -r /tmp/s1 .agents/skills/ui-ux-pro-max
# и так же остальные; затем удалить вложенные .git
find .agents/skills -name .git -type d -prune -exec rm -rf {} +
```

После этого в `AGENTS.md` явно прописана строка «перед работой над UI прочитай `.agents/skills/ui-ux-pro-max/SKILL.md`» — это работает всегда, независимо от того, автоподхватывает Codex папку или нет.

### Шаг 7. Положить конфиг Codex

Всё уже лежит на своих местах в скелете репозитория: `.codex/config.toml`, `AGENTS.md`, `Makefile`, `checkpoint.sh`, `docs/PROMPTS.md`. Роль A пушит скелет, остальные получают через `git pull`.

Если проектный конфиг по какой-то причине не подхватился (профиль `hack` не найден) — два запасных пути:

```bash
cp .codex/config.toml ~/.codex/config.toml            # глобально
# или задать флагами прямо при запуске:
codex -c approval_policy=never -c sandbox_mode=workspace-write
```

### Шаг 8. Прогреть окружение

```bash
python3 -m venv ~/.venvs/hack && source ~/.venvs/hack/bin/activate
pip install openai pydantic streamlit pytest python-dotenv pandas pymupdf pillow ortools
```

`ortools` — только если команда рассматривает задачи № 5 HaulDispatch / № 9 NPT Investigator.

### Шаг 9. Репетиция (обязательно, 45–60 минут)

Накануне прогнать сокращённый цикл на игрушечной задаче: «сделай CLI, который валидирует JSON по Pydantic-схеме и печатает отчёт с ссылками на строки». Цель не код, а проверить: агент в профиле `hack` работает без запросов подтверждения, коммитит, пушит в GitHub, а `make smoke` зелёный. Все три машины, одновременно, в один репозиторий.

# ЧАСТЬ II. Общий репозиторий GitHub

### 2.1. Настройка (делает роль A, один раз)

1. GitHub → **New repository**, приватный, название `hackalem-permitguard`, без README (скелет свой).
2. **Settings → Collaborators** → добавить двоих с правом **Write**. Они получат приглашение на почту — проследите, чтобы приняли до хакатона, иначе первый push упрётся в 403.
3. **Ветку `main` не защищать.** По умолчанию она и так открыта; если включили Rulesets или Branch protection — выключите. На 5 часов ревью через pull request роскошь; защищаемся не процессом, а разделением каталогов.
4. Запушить скелет (см. 2.3) и сказать в чат команды: «репозиторий готов, клонируйте».

### 2.2. Настройка (делает каждый, на своей машине)

```bash
ssh-keygen -t ed25519 -C "hackalem"          # если ключа ещё нет
cat ~/.ssh/id_ed25519.pub                     # GitHub → Settings → SSH and GPG keys → New SSH key
git config --global user.name  "Имя Фамилия"
git config --global user.email "почта-от-github@example.com"
git clone git@github.com:<владелец>/hackalem-permitguard.git
cd hackalem-permitguard
```

Проверка: `ssh -T git@github.com` отвечает «Hi <ник>! You've successfully authenticated, but GitHub does not provide shell access.» Это успех, несмотря на формулировку и ненулевой код возврата.

Полезно, но не обязательно: `gh` CLI (`brew install gh` / `apt install gh`), затем `gh auth login`. С ним ECC-скилл `$github-ops` умеет работать с issues и PR без ухода в браузер.

### 2.3. Скелет репозитория и карта владения

Параллельная работа держится **не на ветках, а на непересекающихся каталогах**. Ветки — дополнительная страховка.

```
hackalem-permitguard/
├── AGENTS.md                ← A (единственный владелец)
├── .codex/config.toml       ← A
├── Makefile                 ← A
├── requirements.txt         ← A
├── .env.example             ← A   (.env в .gitignore!)
├── core/                    ← A   schemas.py, mock_api.py, orchestrator.py, prooflinks.py
├── eval/                    ← A   run.py, metrics.py
├── data/                    ← B   generator.py, fixtures/, ground_truth.json
├── extract/                 ← B   extractor.py, vision.py, prompts/
├── rules/                   ← C   engine.py, matrix.yaml, verdict.py
├── ui/                      ← C   app.py, replay/, assets/
├── checkpoint.sh            ← A   часовая отчётность
├── docs/
│   ├── PROMPTS.md           ← промпты всех ролей
│   ├── setup/               ← этот регламент и скрипты установки
│   ├── pitch/               ← C
│   ├── status/              ← A   автоотчёты чекпоинтов
│   └── requests/{a,b,c}.md  ← у каждого свой файл, конфликтов нет
└── .agents/skills/          ← A (вендоренные внешние скиллы)
```

**Железное правило для агента** (оно прописано в `AGENTS.md`): агент создаёт и меняет файлы **только в своих каталогах**. Нужна правка в чужом — пишет строку в `docs/requests/<своя-буква>.md` и продолжает работу с заглушкой.

### 2.4. Git-протокол

```bash
# перед каждым пушем — всегда:
git pull --rebase origin main
git add core/ eval/          # ТОЛЬКО свои каталоги, никогда git add -A из корня
git commit -m "[A] contract: permit result schema v1"
git push origin main
```

- Пушить **каждые 10–15 минут**. Маленькие коммиты — дешёвый откат.
- Префикс коммита `[A]` / `[B]` / `[C]` — чтобы на чекпоинте было видно, кто что двинул.
- `git push --force` запрещён абсолютно. Это прописано в `AGENTS.md` и в промптах.
- Конфликт всё же случился → не разбирать руками: `git rebase --abort`, вынести свою правку в отдельную ветку `feat/<буква>-<что>`, пушнуть её, и пусть роль A смержит.
- Рискованный эксперимент — в отдельном worktree, чтобы не ломать рабочую копию:
  ```bash
  git worktree add ../exp-ocr -b exp/ocr
  ```

### 2.5. Что даёт GitHub сверх обычного git

ECC знает GitHub нативно, и это можно использовать бесплатно, не меняя протокол:

- `$github-ops` — работа с issues и PR из сессии Codex.
- `/code-review` и `/review-pr` — если всё же понадобится разобрать чей-то PR (например, спорную правку в `core/` после заморозки контракта, которую роль A хочет посмотреть отдельно).
- `gh pr create --fill` — вынести рискованную ветку на обсуждение за одну команду.

Чего **не** делать: включать GitHub Actions. CI на хакатоне съедает минуты ожидания и ничего не добавляет — ворота приёмки гоняются локально через `make`.

# ЧАСТЬ IV. Рабочий цикл: как агент делает работу, а вы контролируете

Один цикл ≈ 25–30 минут. За 5 часов их 8–9.

### Фаза 1 — Запуск сессии (1 минута)

```bash
cd hackalem-permitguard && source ~/.venvs/hack/bin/activate
codex -p hack
```

Профиль `hack` = `approval_policy = "never"` + `sandbox_mode = "workspace-write"`: агент не спрашивает разрешения на каждую правку и каждую команду. Это и есть «ECC делает работу за нас». Защита — в `AGENTS.md` (запрещённые операции) и в том, что песочница ограничена рабочим каталогом.

### Фаза 2 — Кикофф (2 минуты вашего времени)

Вставляете свой ролевой промпт из `docs/PROMPTS.md`. Агент **сначала пишет план** в `docs/plan-<буква>.md` и останавливается.

### Фаза 3 — Приёмка плана (60 секунд вашего времени)

Читаете план и проверяете ровно четыре вещи:

- он не лезет в чужие каталоги;
- он не переизобретает контракт из `AGENTS.md`;
- первый шаг даёт работающий кусок, а не «настройку инфраструктуры»;
- есть явный критерий «готово», который можно проверить командой.

Ответ — одно из двух: `одобрено, выполняй` либо одна исправляющая фраза. Не переписывайте план сами.

### Фаза 4 — Исполнение (20–25 минут, вы в это время не мешаете)

Агент кодит, запускает тесты, чинит себя. Ваше дело — смотреть в терминал краем глаза и ловить два симптома:

- **зацикливание** (третий раз правит один и тот же файл) → Фаза 6;
- **тихая подмена задачи** (начал писать «упрощённую версию») → одна фраза: `стоп. Требование из AGENTS.md §"Жёсткие правила" не опционально. Верни fail-closed логику.`

### Фаза 5 — Закрытие цикла (3 минуты)

```
$verification-loop
```

затем руками, своими глазами:

```bash
make smoke          # сквозной прогон на 1 комплекте
python -m eval.run  # метрики: recall по 20 нарушениям, 0 ложных approve
```

Зелено → `git pull --rebase && git push`. Красное → цикл не закрыт, идём в Фазу 6.

### Фаза 6 — Что делать, когда застряли (правило 10 минут)

| Симптом | Действие |
|---|---|
| Баг не чинится 10 минут | Новая сессия + `$orch-fix-defect` с точным описанием и командой воспроизведения |
| Контекст > 70% | `$strategic-compact`, а лучше — закрыть сессию и открыть новую (`AGENTS.md` вернёт весь нужный контекст) |
| Агент спорит / извиняется по кругу | Закрыть сессию. Разговор не лечится разговором |
| Нужна правка в чужом каталоге | Строка в `docs/requests/<буква>.md` + заглушка у себя. Никогда не править чужое молча |
| Всё сломалось | `git reset --hard <последний зелёный коммит>` — потому и коммитим каждые 15 минут |

### Чего НЕ делать контролёру

Не читать каждый дифф. Не просить «отрефактори покрасивее». Не менять контракт после T+45. Не давать двум своим сессиям Codex писать в один каталог одновременно.

| Время | Роль A | Роль B | Роль C | Контрольная точка |
|---|---|---|---|---|

Чекпоинт = 5 минут, стоя, каждый называет: зелёный/красный, что делает агент, чего ждёт от других.

Таймер и отчётность держит роль A через `checkpoint.sh` (лежит в корне репозитория):

```bash
./checkpoint.sh start                  # один раз, в момент объявления старта
git add .hack-t0 && git commit -m "[A] ops: T+0" && git push   # чтобы отсчёт был общий
./checkpoint.sh --loop 60 --commit     # дальше висит в отдельном терминале до конца
```

Остальные двое смотрят срез у себя, когда нужно: `./checkpoint.sh --quick` (без прогона тестов, три секунды). Отчёты копятся в `docs/status/T+NNN.md` — к концу дня это готовая хронология для организаторов.

# ЧАСТЬ VI. Критерии приёмки (это же — критерии жюри)

Из условия трека, § «Общие технические правила»: они не пожелания, а условия начисления баллов.

- [ ] Каждое значимое утверждение имеет **prooflink**: `source_id` + `location` (страница/строка) + цитата.
- [ ] Система умеет говорить `unknown` / `insufficient_evidence` / `contested`. Уверенная выдумка штрафуется сильнее осторожного пропуска.
- [ ] **Минимум один вызов mock-API** в каждом прогоне (`employee_clearance`, `gas_test_status`, `asset_isolation`, `site_restrictions`).
- [ ] **Минимум один детерминированный валидатор**: Pydantic + правила в коде. Вычисления — кодом, не «моделью на глаз».
- [ ] **HITL**: система не «разрешает» работы, а формирует рекомендацию уполномоченному лицу. Статусы: `approve` / `approve_with_conditions` / `block_and_escalate`.
- [ ] **Fail-closed**: неполные данные → не `approve`, а «требуется решение уполномоченного лица».
- [ ] **Replay-режим**: один клик воспроизводит «вау»-сценарий для жюри.
- [ ] Автотест: точность по 20 зашитым нарушениям, **ноль ложных approve** на критических кейсах.
- [ ] Формат результата — ровно тот JSON из § 5.1 условия (`task_id`, `run_id`, `status`, `findings[]`, `unknowns`, `audit_log`).

# ЧАСТЬ VIII. Питч (3 минуты)

Формула из вводных документов — продаём не код, а траекторию:

1. **0:00–0:30** Боль: проверка одного наряда — 10–25 минут вручную, цена пропущенного барьера — жизнь. Владелец процесса: директор по промбезопасности.
2. **0:30–1:40** Живое демо: «пакет бумаги» → кнопка «Проверить перед началом работ» → красная карточка **«Работы не начинать»**, два барьера, ссылка на источник каждого факта, готовый запрос мастеру.
3. **1:40–2:10** Почему это не чат-бот: детерминированные правила в коде, вызовы реестров, fail-closed, HITL, честный `unknown`.
4. **2:10–2:50** Траектория A → B → C: сегодня класс A (синтетика), пилот класса B на обезличенной выгрузке за 4–8 недель с измеримым KPI, класс C внутри периметра через механизм 1% на НИОКР. Адресаты: ТШО, KPO, Qarmet.

Готовить должна роль C через `$frontend-slides`; схему архитектуры — через `diagram-design`. Текст слайдов — 6 слайдов максимум.

Роли и протокол не меняются — меняется начинка слоёв. Роль A правит блок задачи в `AGENTS.md` за 10 минут, остальное едет как есть.

|---|---|---|---|---|

| **№ 8 TenderTwin** | кросс-сверка + red-team | ТЗ, КП, сертификаты | матрица «требование → поставщик → доказательство» | много похожих решений |
