# HackAlem · Вариант «одна машина» — боевой регламент

**Конфигурация:** один компьютер. На нём три изолированных окружения Codex (три аккаунта) и три идентичности GitLab (три аккаунта), один общий репозиторий GitLab. Три агента работают параллельно в трёх дорожках (lanes), люди контролируют их вместе, за одним экраном.

Всё, что не касается установки и git-идентичностей, берётся из основного регламента без изменений: роли, контракт, чекпоинты, критерии приёмки, питч. Этот файл заменяет **Часть I** и **Часть II** основного runbook'а и добавляет специфику одной машины.

---

## 0. Зачем вообще три аккаунта на одной машине

Три причины, и все практические:

1. **Квоты.** Упёрлись в лимит на аккаунте A — дорожка переезжает на аккаунт B за 5 секунд (смена одной переменной окружения). На пятичасовом хакатоне с тремя параллельными агентами это самый вероятный отказ.
2. **Изоляция сессий и контекста.** У каждой дорожки своя история, свои сессии, свой кэш плагина. Агент дорожки B не подхватит мусор из контекста дорожки A.
3. **Атрибуция в GitLab.** Коммиты приходят от трёх разных авторов — видно, кто (точнее, чей агент) что двинул, и это же нужно для отчётности организаторам, если они смотрят репозиторий.

Оборотная сторона: ECC придётся поставить **трижды** — по одному разу в каждый `CODEX_HOME`. Состояние плагина хранится именно в активном home, общего для машины нет.

# ЧАСТЬ I-A. Подготовка машины (накануне, 60–80 минут)

### Шаг 1. Предусловия

```bash
node -v          # >= 20 (минимум 18)
python3 -V       # >= 3.11
git --version
codex --version
tmux -V          # желательно: три дорожки удобнее в панелях
```

### Шаг 2. Три окружения Codex

Codex хранит авторизацию в `$CODEX_HOME/auth.json`, по умолчанию это `~/.codex`. Делаем три отдельных дома:

```bash
mkdir -p ~/.codex-a ~/.codex-b ~/.codex-c
```

Для каждого — свой вход, **строго по одному аккаунту на дом**:

```bash
CODEX_HOME=~/.codex-a codex login     # аккаунт человека A
CODEX_HOME=~/.codex-b codex login     # аккаунт человека B
CODEX_HOME=~/.codex-c codex login     # аккаунт человека C
```

Проверка, что дома действительно разные:

```bash
ls -l ~/.codex-a/auth.json ~/.codex-b/auth.json ~/.codex-c/auth.json
CODEX_HOME=~/.codex-a codex exec "ответь одним словом: ок"
```

> Если браузерный вход путается между аккаунтами — логиньтесь в трёх разных профилях браузера или в приватном окне для второго и третьего.

### Шаг 3. ECC — три раза, по одному в каждый дом

```bash
for H in a b c; do
  CODEX_HOME=~/.codex-$H codex plugin marketplace add affaan-m/ECC
  CODEX_HOME=~/.codex-$H codex plugin add ecc@ecc
  CODEX_HOME=~/.codex-$H codex plugin list --json
done
```

Офлайн-резерв из вашего архива (распаковать один раз, ставить из локального пути во все три дома):

```bash
unzip ECC-main.zip -d ~/tools && mv ~/tools/ECC-main ~/tools/ECC
cd ~/tools/ECC && npm install --ignore-scripts --no-audit --no-fund
for H in a b c; do
  CODEX_HOME=~/.codex-$H codex plugin marketplace add "$HOME/tools/ECC"
  CODEX_HOME=~/.codex-$H codex plugin add ecc@ecc
done
node ~/tools/ECC/scripts/codex/check-plugin-cache.js
```

Проверка в каждом доме (внутри интерактивной сессии): `/plugins` → ECC enabled, затем один раз `$configure-ecc`.

Что не делаем: не запускаем `scripts/sync-ecc-to-codex.sh` (конфликтует с нативным плагином) и не включаем хуки в `/hooks`.

### Шаг 4. Три идентичности GitLab

Три ключа:

```bash
ssh-keygen -t ed25519 -N "" -f ~/.ssh/gl_a -C "hackalem-a"
ssh-keygen -t ed25519 -N "" -f ~/.ssh/gl_b -C "hackalem-b"
ssh-keygen -t ed25519 -N "" -f ~/.ssh/gl_c -C "hackalem-c"
cat ~/.ssh/gl_a.pub ~/.ssh/gl_b.pub ~/.ssh/gl_c.pub
```

Каждый публичный ключ добавляется **в свой** аккаунт GitLab: Preferences → SSH Keys.

Три хост-алиаса в `~/.ssh/config`:

```
Host gitlab-a
    HostName gitlab.com
    User git
    IdentityFile ~/.ssh/gl_a
    IdentitiesOnly yes

Host gitlab-b
    HostName gitlab.com
    User git
    IdentityFile ~/.ssh/gl_b
    IdentitiesOnly yes

Host gitlab-c
    HostName gitlab.com
    User git
    IdentityFile ~/.ssh/gl_c
    IdentitiesOnly yes
```

`IdentitiesOnly yes` обязателен: без него ssh переберёт все ключи и залогинит вас не тем аккаунтом. Проверка:

```bash
ssh -T gitlab-a   # должен поздороваться с аккаунтом A
ssh -T gitlab-b
ssh -T gitlab-c
```

### Шаг 5. Три рабочих копии, а не три worktree

```bash
mkdir -p ~/hack
git clone git@gitlab-a:<группа>/hackalem-permitguard.git ~/hack/a
git clone git@gitlab-b:<группа>/hackalem-permitguard.git ~/hack/b
git clone git@gitlab-c:<группа>/hackalem-permitguard.git ~/hack/c
```

Обратите внимание на алиас хоста в URL — он и определяет, под каким аккаунтом пойдёт push.

Локальная идентичность в каждой копии (не глобальная!):

```bash
cd ~/hack/a && git config user.name "Имя A" && git config user.email "почта-A@example.com"
cd ~/hack/b && git config user.name "Имя B" && git config user.email "почта-B@example.com"
cd ~/hack/c && git config user.name "Имя C" && git config user.email "почта-C@example.com"
```

**Почему три клона, а не три `git worktree`:** worktree'ы делят один `.git` и не могут одновременно стоять на ветке `main`, а весь наш протокол построен на прямом пуше в `main`. Три независимых клона стоят 30 МБ диска и снимают проблему целиком. Плюс каждая копия имеет свой remote-алиас, то есть свой аккаунт GitLab — с worktree так не получится.

### Шаг 6. Общее Python-окружение

Одно на всех, каталоги кода всё равно разные:

```bash
python3 -m venv ~/.venvs/hack
source ~/.venvs/hack/bin/activate
pip install openai pydantic streamlit pytest python-dotenv pandas pymupdf pillow fpdf2 pyyaml
# при выборе HaulDispatch / NPT Investigator: pip install ortools
```

Ключ OpenAI: у каждой дорожки свой `.env` в своей копии (`~/hack/a/.env` и т. д.). Если ключ один на команду — положите один и тот же во все три, но помните про общий rate limit.

### Шаг 7. Скрипт запуска дорожки

Положите `lane.sh` из комплекта в `~/hack/` и сделайте исполняемым. Дальше запуск дорожки — одна команда:

```bash
~/hack/lane.sh a          # интерактивная сессия Codex дорожки A
~/hack/lane.sh b
~/hack/lane.sh c
```

### Шаг 8. Репетиция (обязательно, 45 минут)

Прогнать накануне на игрушечной задаче, **одновременно во всех трёх дорожках**, и убедиться в четырёх вещах: три сессии Codex работают параллельно и не тормозят машину; каждая пушит в `main` под своим аккаунтом (проверить в GitLab → Commits, авторы должны различаться); `git pull --rebase` не порождает конфликтов; `make smoke` зелёный.

# ЧАСТЬ II-A. Как это выглядит во время работы

### Раскладка экрана

Три панели tmux — по дорожке в каждой, плюс четвёртая для контроля:

```bash
tmux new -s hack
# Ctrl-b %   — разделить вертикально
# Ctrl-b "   — разделить горизонтально
```

| Панель | Что запущено | Кто смотрит |
|---|---|---|
| 1 | `~/hack/lane.sh a` — ядро и контракт | человек A |
| 2 | `~/hack/lane.sh b` — данные и извлечение | человек B |
| 3 | `~/hack/lane.sh c` — правила и витрина | человек C |
| 4 | контроль: `./checkpoint.sh --loop 60 --commit` из `~/hack/a` | тот, кто ведёт чекпоинт |

Клавиатура одна, поэтому очередь на ввод. Это не мешает: во время фазы исполнения агенту ничего вводить не нужно, а фаза приёмки плана занимает 60 секунд.

### Порты не должны пересекаться

Streamlit и любые локальные сервисы — с явным портом:

```bash
streamlit run ui/app.py --server.port 8501   # дорожка C, витрина
streamlit run ui/app.py --server.port 8502   # вторая копия для сравнения
```

В `Makefile` цель `ui` фиксирует порт 8501, чтобы демо всегда открывалось по одному адресу.

### Фоновый режим: агент работает, вы не сидите в терминале

На одной машине это особенно удобно — интерактивную сессию держим только для той дорожки, которую сейчас ведём, остальные запускаем безголовно с логом в файл:

```bash
cd ~/hack/b && source ~/.venvs/hack/bin/activate
CODEX_HOME=~/.codex-b codex exec --full-auto \
  "$(cat ~/hack/prompts/kickoff-b.txt)" 2>&1 | tee ~/hack/logs/b-$(date +%H%M).log
```

Продолжить прерванную безголовую сессию:

```bash
CODEX_HOME=~/.codex-b codex exec resume --last "Доведи eval до зелёного, ничего постороннего не рефактори."
```

Смотреть, что происходит, не мешая:

```bash
tail -f ~/hack/logs/b-*.log
```

Ограничение безголового режима: агент не спросит вас ни о чём. Поэтому запускайте его так **только после того, как план утверждён** в интерактивной сессии — иначе он молча уедет не туда на 20 минут.

### Переключение аккаунта при исчерпании квоты

Дорожка привязана к дому только переменной окружения. Если у B кончился лимит:

```bash
cd ~/hack/b && CODEX_HOME=~/.codex-a codex -p hack     # та же копия кода, другой аккаунт
```

Git-идентичность при этом не меняется — коммиты по-прежнему уйдут от аккаунта GitLab B, потому что она задана в самой копии. Это ровно то поведение, которое нужно.

## Git-протокол (отличия от версии с тремя машинами)

Всё то же самое, с тремя поправками:

1. **Всегда проверяйте, в какой копии вы находитесь.** Самая частая ошибка одной машины — набрать команду дорожки B в каталоге дорожки A. Лечится приглашением оболочки: `lane.sh` выставляет `PS1` с крупной пометкой `[LANE A]`.
2. **Не открывайте один и тот же файл в двух копиях.** Разделение каталогов из `AGENTS.md` действует буквально так же, как на трёх машинах.
3. **`git pull --rebase` перед каждым пушем** — здесь это ещё важнее: три агента пушат в один `main` с интервалом в минуты.

## Аварийные сценарии, специфичные для одной машины

| Что случилось | Что делать |
|---|---|
| Машина тормозит, три сессии + Streamlit не тянет | Перевести дорожку A в безголовый режим (`codex exec`), закрыть лишние вкладки браузера; Streamlit держать один |
| Push ушёл не от того аккаунта | Проверить `git remote -v` в копии — там должен быть алиас `gitlab-a/b/c`, а не `gitlab.com`. Исправить: `git remote set-url origin git@gitlab-b:<группа>/<репо>.git` |
| `ssh -T gitlab-b` здоровается именем A | В `~/.ssh/config` не хватает `IdentitiesOnly yes`, либо ключ A загружен в ssh-agent: `ssh-add -D` |
| ECC виден в одном доме и не виден в другом | Плагин ставится в каждый `CODEX_HOME` отдельно. Повторить шаг 3 для этого дома |
| Кончилась квота у одного аккаунта | Перевести дорожку на другой `CODEX_HOME` (см. выше). Это и есть главная выгода схемы |
| Машина умерла | Это единственная точка отказа схемы. Митигация: пуш каждые 10–15 минут + один запасной ноутбук с установленным Codex, на который можно склонировать репозиторий за 3 минуты |

## Что осталось без изменений

- Роли, карта владения каталогами, контракт результата — основной `AGENTS.md` (в комплекте есть его версия для одной машины: в §6 прописаны remote-алиасы).
- Кикофф-промпты, управляющие фразы, аварийные и питч-промпты — `docs/PROMPTS.md` в репозитории, менять ничего не нужно. Сохраните кикоффы в файлы `~/hack/prompts/kickoff-{a,b,c}.txt`, чтобы подставлять их в `codex exec`.
- Таймлайн, чекпоинты и критерии приёмки — `RUNBOOK-3-MACHINES.md`, Части V–VIII.

**Отчётность.** `checkpoint.sh` лежит в корне каждой копии, но `start` и `--loop … --commit` делает только дорожка A из `~/hack/a` — иначе три копии начнут драться за `docs/status/`:

```bash
cd ~/hack/a && source ~/.venvs/hack/bin/activate
./checkpoint.sh start && git add .hack-t0 && git commit -m "[A] ops: T+0" && git push
./checkpoint.sh --loop 60 --commit
```

Дорожки B и C пользуются только `./checkpoint.sh --quick` в своих копиях.
