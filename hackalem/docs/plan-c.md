# План роли C: правила и витрина PermitGuard

## Цель и границы

Собрать детерминированный слой правил и безопасную витрину, которые принимают данные по контракту `core/schemas.py`, не додумывают отсутствующие факты и всегда оставляют итоговое решение человеку. Реализация ограничена каталогами `rules/`, `ui/` и `docs/pitch/`; изменения контрактов, извлечения, данных и оркестратора выполняются только их владельцами.

Порядок работы: сначала один сквозной ловушечный комплект, затем покрытие всех восьми правил, после этого UI/replay и полная проверка. Перед версткой обязательно прочитать `.agents/skills/ui-ux-pro-max/SKILL.md`.

## 1. Зафиксировать интерфейсы роли C

Файлы для чтения: `core/schemas.py`, `core/mock_api.py`, `core/orchestrator.py`, `docs/requests/a.md` (если существуют). Изменяемые файлы на этом шаге: нет.

- Выписать фактические Pydantic-типы входа, `Finding`, `Prooflink`, `Validation`, итогового результата и допустимые enum-значения.
- Определить единый вызов движка и агрегатора без дублирования схем из `core/`.
- Зафиксировать, откуда приходят время начала работ, смена, зона, работники, подписи, газоанализ, LOTO, одновременные работы, перечень файлов и ответы mock-реестров.
- Для отсутствующего документа использовать доказательство из манифеста/перечня входного пакета; не создавать finding без существующего `source_id`, реального `location` и точной `quote`.
- Если контракт не предоставляет обязательное поле, оформить запрос роли A в `docs/requests/c.md`, а в своей реализации оставить явную fail-closed ветку.

Критерий готовности: все входы восьми правил сопоставлены с полями контракта; нет локальных копий моделей и не требуется правка чужих каталогов.

## 2. Матрица из восьми правил

Файл: `rules/matrix.yaml`.

Каждая запись содержит `rule_id`, русское описание, `severity` (`P1`/`P2`/`P3`), детерминированное условие, обязательные источники и `required_human_decision`. Идентификаторы стабильны и совпадают с движком, тестами и ground truth.

| Правило | Проверка | Базовый риск |
|---|---|---|
| `R-GAS-01` | Газоанализ существует и действителен на момент начала работ | P1 |
| `R-EMP-01` | Допуск каждого назначенного работника действует на весь интервал работ | P1 |
| `R-SIG-01` | Обязательная подпись ответственного присутствует и доказуема | P1 |
| `R-ZONE-01` | Разрешенная зона работ совпадает с зоной наряда | P1 |
| `R-LOTO-01` | Требуемая LOTO-изоляция подтверждена документом и mock-реестром | P1 |
| `R-SIMOPS-01` | Нет несовместимых одновременных работ с пересекающимися зоной и временем | P1 |
| `R-SHIFT-01` | Полный интервал работ находится внутри разрешенной смены | P2 |
| `R-PACK-01` | Пакет содержит все обязательные типы документов и источники | P2 |

Для каждого правила отдельно описать результат при отсутствии, противоречии и невалидном формате входа. Эти состояния не считаются успешной проверкой и передаются в fail-closed агрегацию.

Критерий готовности: YAML корректно разбирается; ровно восемь уникальных `rule_id`; у каждой записи заполнены все обязательные поля и решение человека; каждое условие имеет однозначный проверяемый смысл.

## 3. Детерминированный движок правил

Файл: `rules/engine.py`.

- Загрузить и валидировать матрицу; неизвестный/дублирующийся `rule_id` считать ошибкой конфигурации.
- Нормализовать даты и время с явной временной зоной; сроки, границы смен и пересечения интервалов вычислять только Python-кодом.
- Реализовать восемь независимых проверок и общий запуск в стабильном порядке `rule_id`.
- Для сработавшего правила формировать `Finding` строго через модели `core/schemas.py`: severity и действие человека брать из матрицы, а prooflinks только из входных данных.
- Не переносить вывод extractor или mock-API в `confirmed`, если источники спорят: использовать `contested`; отсутствие обязательного подтверждения классифицировать как `insufficient_evidence`; неразрешимую неопределенность помечать `unknown`.
- Никогда не синтезировать цитату, местоположение, confidence или факт для прохождения схемы. Невалидный prooflink не выдавать как подтвержденный результат.
- Добавить запись в audit log для каждой выполненной проверки: правило, входные источники, исход и причина, без секретов и персональных данных сверх входного контракта.

Первый вертикальный срез: ловушечный комплект с просроченным газоанализом проходит через `R-GAS-01`, дает P1 finding с реальным prooflink и передается агрегатору.

Критерий готовности: одинаковый вход всегда дает одинаковый упорядоченный результат; все восемь правил возвращают объекты контрактных моделей; граничные значения времени и интервалов обработаны явно; каждый finding имеет хотя бы один валидный prooflink.

## 4. Fail-closed вердикт

Файл: `rules/verdict.py`.

Политика агрегации:

- Любой P1 -> `block_and_escalate`.
- Любой P2 -> `block_and_escalate`, пока уполномоченный человек не устранит барьер или не предоставит подтверждение.
- Отсутствующий обязательный источник -> `block_and_escalate` и `insufficient_evidence`.
- Противоречивые данные, неизвестное правило, ошибка разбора матрицы или невозможность проверить обязательное условие -> `block_and_escalate`.
- Только P3 при полном комплекте подтверждений -> `approve_with_conditions`.
- `approve` допустим только при полном наборе обязательных источников, успешном прохождении всех правил и отсутствии findings/unknowns; это рекомендация, а не разрешение начать работу.
- Во всех ветках результата и findings сохранять `requires_human_review = true` и непустое `required_human_decision`.

Приоритет результата не зависит от порядка findings. Более опасный исход всегда доминирует; исключение или нераспознанное состояние не может привести к `approve`.

Критерий готовности: таблица решений полностью покрыта unit-тестами; нет ветки, где неполные, противоречивые или технически невалидные данные дают `approve`/`approve_with_conditions`.

## 5. Streamlit UI

Файлы: `ui/app.py`, при необходимости статические файлы в `ui/assets/`.

- Выбор доступного комплекта и основная кнопка «Проверить перед началом работ».
- Во время проверки показывать устойчивое состояние выполнения; исключение отображать как блокировку и необходимость ручной проверки, а не как успешный результат.
- Для `block_and_escalate` показать главный красный статус «РАБОТЫ НЕ НАЧИНАТЬ» и список барьеров по приоритету.
- Каждый барьер раскрывает `rule_id`, причину, классификацию, файл, страницу/строку, точную цитату и «Требуется решение: ...».
- `unknown`, `contested` и `insufficient_evidence` выводить отдельным заметным серым блоком, не скрывать в деталях.
- Для безопасного результата не писать, что система разрешила работу: показывать рекомендацию и обязательное решение уполномоченного человека.
- Не выводить внутренние трассировки и секреты; сохранить доступность, читаемость с проектора и корректную работу на узком экране.

Критерий готовности: ловушечный комплект за один пользовательский сценарий приводит к красному статусу; два барьера и их prooflinks раскрываются без перезагрузки; неизвестные данные видимы; HITL-текст присутствует при любом вердикте.

## 6. Однокнопочный replay

Файлы: `ui/replay/` (конфигурация/фикстура и код загрузки), интеграция в `ui/app.py`.

- Заранее выбрать стабильный ловушечный комплект минимум с двумя доказуемыми барьерами, один из которых P1.
- Replay использует тот же движок и компоненты результата, что обычный режим; отдельной «красивой» логики вердикта нет.
- Один клик загружает комплект, запускает проверку и показывает детерминированный результат; отсутствие внешнего API обрабатывается заранее предусмотренным фиктивным JSON по контракту.
- Проверить повторный запуск в той же сессии и чистый старт Streamlit.

Критерий готовности: replay воспроизводится локально не менее трех раз с одинаковыми rule_id, verdict и prooflinks; ни одна ссылка не указывает на несуществующий файл/строку/страницу.

## 7. Тесты роли C

Файлы: `rules/tests/test_matrix.py`, `rules/tests/test_engine.py`, `rules/tests/test_verdict.py`, `ui/tests/test_app.py` (или существующие тестовые пути внутри каталогов роли C, если они уже заданы проектом).

- Матрица: схема YAML, восемь уникальных правил, допустимые severity, непустые источники и человеческие решения.
- Движок: положительный и отрицательный сценарий каждого правила; отсутствующие поля; неверные форматы; противоречивые источники; реальные prooflinks.
- Время: точная граница срока, одна секунда до/после, переход суток, временная зона, вложенные и частично пересекающиеся интервалы.
- Вердикт: P1, P2, только P3, чистый полный пакет, отсутствие источника, unknown, contested, пустой список, исключение/неизвестное правило и независимость от порядка findings.
- Безопасностные инварианты: ноль `approve` при критическом нарушении; любой finding имеет валидный prooflink; HITL-поля всегда заполнены; ошибка никогда не открывает доступ.
- UI: выбор комплекта, нажатие кнопки, красный статус, раскрытие prooflinks, отображение unknown и replay одним кликом.

Критерий готовности: все тесты роли C стабильны без сети и проходят повторно; тесты проверяют содержание результата, а не только отсутствие исключения.

## 8. Интеграция и общая готовность

Последовательность проверки после реализации:

1. Запустить узкие тесты `rules/` и `ui/`.
2. Запустить `make smoke` на одном ловушечном комплекте.
3. Запустить `make eval` и проверить recall по 20 нарушениям >= 0.8, ложные `approve` на критических кейсах = 0.
4. Запустить `make test` и убедиться, что весь pytest зеленый.
5. Вручную пройти обычный UI и replay, сверив каждый показанный prooflink с исходным файлом.

Итоговые критерии готовности роли C:

- Реализованы и протестированы ровно восемь правил матрицы.
- Арифметика дат и интервалов выполняется кодом, результат детерминирован.
- Неполные, спорные и ошибочные данные закрываются через `block_and_escalate`.
- Каждый finding доказуем через существующие `source_id`, `location`, `quote`.
- UI явно показывает барьеры, unknowns и обязательное человеческое решение.
- Replay стабильно демонстрирует ловушечный комплект одним кликом.
- `make smoke`, `make eval`, `make test` завершены успешно; иначе работа не объявляется готовой.

После утверждения этого плана начать с шага 1 и первого вертикального среза. До подтверждения реализацию не писать.
